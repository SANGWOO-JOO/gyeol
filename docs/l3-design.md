# L3 설계: 근거 있는 추천 (2026-10-27 승인)

전체 설계(`docs/design-v3.md` 12장)의 L3 "RAG 지식 인입, 임베딩 서비스, 곡 설명 보강, 추천과 이유, 피드백". 면접용 수치 5번 "RAG를 켰을 때와 껐을 때의 곡 설명 정확도와 추천 좋아요 비율"이 결과물이다.

## 1. 목표

식별된 곡마다 **출처가 있는 설명**(분위기·장르·템포·보컬·시대)을 만들고, 그 설명과 청취 데이터로 **추천 20곡과 이유**를 보여 준다. 추천마다 좋아요·별로를 받아 RAG를 켰을 때와 껐을 때를 비교한다.

## 2. 흐름

```
식별 완료 (L2)
 └▶ SQS:enrich ─▶ enrich-worker
       1. 지식 모으기 (fetcher): 곡 → 음반 → 가수 순
          · MusicBrainz 관계: 작곡·작사·편곡·프로듀서, 위키데이터 링크 (CC0)
          · Wikipedia 한·영·일 요약 (CC BY-SA, 출처 표시)
          · Last.fm 위키 요약·태그 (비상업, 출처 표시)
          → knowledge_chunk (출처 URL·라이선스·언어·본문, 짧게)
       2. 곡 설명 (Haiku 4.5): 모은 청크만 근거로 분위기·장르·템포·보컬·시대
          칸마다 근거 청크 ID와 근거 단위(곡/음반/가수), 근거가 없으면 "근거 부족"
          → track_descriptor (검증: 인용한 청크가 실제로 있어야 통과)
       3. 임베딩: 곡 설명 문장 → embed 서비스 → track_vector (pgvector)
 └▶ SQS:profile ─▶ profile-worker
       4. 취향 프로필: 재생 수 로그 가중, 시간대(새벽·출근·주말)별 프로필 벡터
       5. 후보: Last.fm 비슷한 곡·가수 + 우리 DB 벡터 이웃 → 이미 들은 곡·모음 제외 → 후보도 식별·설명 보강 (상위 50곡)
       6. 점수: 취향 벡터 유사도 + 같은 작곡가·프로듀서 가산 + Last.fm 유사도
       7. 상위 50곡 → LLM이 다시 정렬해 20곡과 이유 (설명·청크를 근거로 인용) → recommendation
결과 화면: 취향 요약 + 추천 20곡(표지·이유·출처 링크) + 좋아요/별로 → feedback
```

## 3. 데이터

| 테이블 | 내용 | 보관 |
|---|---|---|
| `knowledge_chunk` | 대상(곡/음반/가수), 출처 URL, 라이선스, 언어, 본문, 가져온 시각 | 계속 (출처 표시) |
| `track_descriptor` | 곡별 칸, 칸마다 근거 단위·청크 ID·신뢰도 | 계속 |
| `track_vector` | 곡 설명 임베딩 | 계속 |
| `taste_profile` | 세션별 취향 벡터(전체·시간대별), 요약 문장 | 30일 |
| `recommendation` / `feedback` | 추천·이유·근거·점수 / 좋아요·별로 | 30일 |

곡 설명·임베딩은 전역 캐시라 사용자가 늘수록 비용이 줄어든다.

## 4. 처리량과 비용 (추정)

| 항목 | 계산 | 금액 |
|---|---|---|
| 곡 설명 (Haiku 4.5) | 곡당 입력 약 1,500·출력 약 300 토큰 → 약 $0.003 | 첫 사용자 약 $0.3 (들은 곡 상위 50 + 후보 50) |
| 추천 다시 정렬과 이유 | 입력 약 8,000·출력 약 2,000 토큰 | Haiku 약 $0.02 / Sonnet 4.6 약 $0.05 |
| 임베딩 | 클러스터 안 CPU 모델 | 0 |
| 외부 API | Wikipedia·Last.fm·MusicBrainz | 0 |

설명 대상을 **들은 곡 상위 50 + 후보 50**으로 제한한다. 300곡 전부면 첫 사용자 약 $1, MusicBrainz 초당 1회 제한으로 수십 분.

## 5. 작업 묶음

| 순서 | 묶음 | 외부 의존 |
|---|---|---|
| L3-0 | 모델과 임베딩 정하기: Sonnet 4.6 호출 확인, 임베딩 후보를 CPU 속도·한국어 품질로 비교 | Bedrock(몇 센트), 모델 내려받기 |
| L3-1 | 지식 인입: fetcher에 Wikipedia·Last.fm 위키·MusicBrainz 관계, `knowledge_chunk`, enrich 큐 | 무료 API |
| L3-2 | 곡 설명 보강 + 정확도 측정(위키 원문과 대조, RAG 켬/끔) | Haiku |
| L3-3 | embed 서비스(별도 컨테이너, HPA 대상), `track_vector` | 없음 |
| L3-4 | 취향 프로필, 후보, 점수, LLM 다시 정렬과 이유, 결과 화면 | Haiku 또는 Sonnet |
| L3-5 | 좋아요·별로, 좋아요 비율, RAG 켬/끔 전환 | 없음 |

## 7. L3-0 결과 (2026-10-27)

**추천 이유용 LLM**: `global.anthropic.claude-sonnet-4-6` 호출 확인(짧은 요청). 서울 지역 프로필(`apac.…`)은 없어 global만. L3-4에서 Haiku 4.5와 같은 평가 세트로 비교한다. (목록에는 Sonnet 5·5.5, Opus 계열도 ACTIVE로 나오지만 Sonnet 5는 호출 시 사용 불가였다. 목록만으로 판단하지 않는다.)

**임베딩 모델: `intfloat/multilingual-e5-small`로 확정** (`tools/embed-eval`, 곡 설명 36문장(6묶음 × 한·영·일)·짧은 요청 12개, 맥북 M1 CPU)

| 항목 | e5-small | paraphrase-multilingual-MiniLM-L12-v2 |
|---|---|---|
| 짧은 요청 → 곡 설명, 1위 정확도 / MRR | **12/12 (100%) / 1.00** | 6/12 (50%) / 0.66 |
| 곡 설명끼리 1위 (e5는 양쪽 "query:") | **67%** | 58% |
| 곡 설명끼리, 같은 언어만 | **61%** | 44% |
| 한국어 설명 → 다른 언어 설명 | **67%** | 56% |
| 100문장 / 1문장 | 0.40초 / 18ms | 0.39초 / 20ms |
| 프로세스 메모리 (PyTorch 포함) | 857MB | 801MB |
| 차원 | 384 | 384 |

- e5는 접두어에 민감하다: 곡 설명끼리를 "passage:"로 비교하면 50%, "query:"로 비교하면 67%. **embed 서비스 API에 질의용/문서용 구분을 둔다.**
- 곡 설명끼리 정확도가 60%대인 것은 평가 세트가 작고(묶음당 6문장) 경계가 애매한 문장이 섞인 탓도 있다. 추천 점수는 벡터 유사도만 쓰지 않고 작곡가·Last.fm 유사도와 섞는다.
- 곡 설명은 LLM이 한 언어로 만들게 한다 (같은 언어끼리 비교가 더 정확).
- 메모리 약 850MB는 PyTorch 탓. L3-3 컨테이너에서는 ONNX Runtime으로 줄이는 것을 검토 (추정).
- 더 큰 `multilingual-e5-base`(약 1.1GB)는 저장 공간(남은 약 9GB)과 CPU 서빙 부담 때문에 비교하지 않았다. MiniLM 모델은 지웠다.

## 8. L3-1 지식 인입 결과 (2026-10-27)

**구성**: V10(`knowledge_chunk`·`knowledge_fetch`·`track_credit`·`enrich_target`, `track.work_mbids`), fetcher `GET /internal/knowledge/{recording|work|release-group|artist}/{mbid}`(MusicBrainz 관계·장르·태그 → 문장 청크, Wikidata → Wikipedia 한·영·일 첫 요약, Last.fm 위키·태그, HTML·"Read more" 제거, 1,200자 문장 단위), worker `EnrichService`·`EnrichListener`(식별이 끝난 세션의 재생 상위 50곡 + 고른 곡, 5곡씩, 대상별 90일 캐시, 외부 503은 30초 뒤, 실패 큐 → FAILED), api `enrich` 진행률, 결과 화면 진행 문구. 고른 곡이 모두 DB 곡이면 api가 바로 보강을 맡긴다.

**채움률** (`tools/knowledge-eval/measure.py`, 실제 API, DB의 실제 곡 41개)

| 대상·출처 | 채움률 |
|---|---|
| Wikipedia 가수 (아무 언어 / 한국어 / 영어 / 일본어) | **100%** / 100% / 97% / 82% |
| Last.fm 가수 | 97% |
| Last.fm 음반 / Wikipedia 음반 | 78% / 73% |
| 작곡·작사 크레딧 (MusicBrainz) | 65% |
| MusicBrainz 녹음 (편곡·프로듀서·태그) | 56% |
| Last.fm 곡 / Wikipedia 곡(작품) | 24% / 21% |
| **곡·음반 단위 설명 근거** (곡·작품·음반의 위키 또는 Last.fm 본문 80자 이상) | **75%** |

- 41곡, 331초(곡당 8.1초, 가수·작품 캐시 포함), 청크 379개. 외부 연결 시간 초과 2번 → 30초 뒤 다시 시도해 모두 완료.
- 청크 평균 길이: Wikipedia 영어 407자 · 한국어 174자 · 일본어 98자, Last.fm 348자, MusicBrainz 문장 81자.
- **곡 단위 지식은 얇다** (곡 문서는 유명곡만). 설계 14장의 위험("국내 곡 데이터가 얇음")이 숫자로 확인됐다 → L3-2 곡 설명은 **근거 단위(곡/음반/가수)를 칸마다 표시**하고, 가수 단위로만 근거가 있으면 신뢰도를 낮게 둔다.
- 이 41곡은 표본으로 고른 유명곡이라 실제 사용자 기록(덜 알려진 곡 포함)에서는 채움률이 더 낮을 것이다 (추정).

**고친 것**: 같은 작품(work)을 공유하는 두 번째 곡에 작곡 크레딧이 붙지 않았다(작품을 캐시로 건너뛰면서). 이미 가져온 작품이면 같은 작품을 공유하는 다른 곡의 작곡·작사 크레딧을 복사한다 — 통합 테스트로 잡음.

## 9. L3-2 곡 설명 보강 결과 (2026-10-27)

**구성**: V11(`track_descriptor`: 요약 + 칸마다 {값, 근거 청크, 근거 단위, 신뢰도}), worker 보강 흐름 끝에 곡 설명(설명이 없거나 지식이 바뀐 곡만, **2곡씩** Haiku 4.5, 근거 청크가 없으면 LLM 없이 "근거 부족"), `DescriptorBuilder`(준 청크 번호만 인정, 근거 단위·신뢰도는 인용한 청크의 대상으로 우리가 계산: 곡·작품 HIGH / 음반 MEDIUM / 가수 LOW, 발매 연대는 MusicBrainz 발매일), `BedrockTool`(도구 호출 공통), 가짜 설명(태그를 장르로), 측정용 `POST /internal/describe/eval`(RAG 켬/끔 + Sonnet 4.6 심판, 로컬 전용). 칸: 장르·분위기·템포·에너지·보컬·시대·요약, 한국어.

**RAG 켬/끔** (`tools/describe-eval`, 지식이 있는 실제 곡 41개, 심판 Sonnet 4.6이 같은 근거 청크로 칸마다 판정)

| 지표 | RAG 켬 | RAG 끔 |
|---|---|---|
| **근거로 뒷받침되는 칸** | **106/132 (80%)** | 33/246 (13%) |
| 채운 칸 / 비운 칸(근거 부족) | 54% / 46% | 100% / 0% |
| 장르 / 요약 | 100% / 97% | 32% / 15% |
| 분위기 / 보컬 | 64% / 62% | 7% / 22% |
| 템포 / 에너지 | 1/5 / 0/5 | 2% / 2% |
| 곡 설명 비용 (단가 추정) | 곡당 약 $0.0026 | 곡당 약 $0.0018 |

- **해석 주의**: "실제로 맞는지"가 아니라 "모은 근거 자료로 뒷받침되는지"다. RAG 끔의 답 일부는 사실일 수 있지만 근거를 댈 수 없다 (예: 015B "텅 빈 거리에서"를 근거 없이 "90년대 한국 록 대표곡"으로 씀).
- RAG 켬은 근거가 없으면 비워 두므로 채움률이 54%. 템포·에너지는 근거 자료에 거의 없어 L3-4 추천 점수에서 쓰지 않는다.
- 신뢰도별(HIGH 59%, MEDIUM 80%, LOW 79%)은 칸 수가 작아(29·41·24) 결론을 내지 않는다.
- 측정 비용 약 $0.95 (첫 시도 포함).

**Bedrock 503**: 첫 측정(5곡 묶음, 입력 약 5,400토큰)에서 503이 27번, RAG 켬 9묶음 중 3묶음만 성공. 2곡 묶음 + 다시 시도 간격 10·20·40초로 바꿔 41곡 모두 처리(503 128번을 재시도로 넘김). 큰 요청일수록 503이 잦은 것으로 보여(추정) 운영 경로도 2곡씩 부른다. global 추론 프로필의 용량 문제로 보이며, EKS 측정 때 처리량 병목 후보다.

## 10. L3-3 embed 서비스 결과 (2026-10-27)

**구성**: `embed/`(Python 3.13 + FastAPI + ONNX Runtime + tokenizers, PyTorch 없음, `POST /embed {texts, kind: query|passage}`, `/healthz`, `/readyz`), 모델은 Hugging Face에 미리 변환된 `onnx/model.onnx`(fp32). V12 `track_vector`(vector(384), HNSW cosine, 문장 해시로 바뀐 곡만 다시). worker 보강 흐름 끝에서 곡 설명 문장("요약: … 장르: … 분위기: … 보컬: …")을 "query" 접두어로 임베딩. 로컬 18084(`scripts/dev-up.sh`), 컨테이너 `deploy/docker/embed.Dockerfile`(모델 포함), Helm Deployment·Service·**HPA**(CPU 70%, 1~4개).

**ONNX 판 측정** (L3-0 평가 세트, 맥북 M1)

| 항목 | PyTorch (L3-0) | **ONNX fp32 (채택)** | ONNX int8 (AVX-512 VNNI용) |
|---|---|---|---|
| PyTorch와 같은 벡터 (최소 코사인) | - | **1.000** | 0.994 |
| 짧은 요청 → 곡 설명 / 곡 설명끼리 | 100% / 66.7% | 100% / 66.7% | 100% / **61.1%** |
| 1문장 지연 | 18ms | **8.4ms** | 5.6ms |
| 최대 / 사용 중 메모리 (그래프 최적화 기본 단계) | 857MB / - | **805MB / 625MB** | 502MB / 423MB (최적화 전부) |
| 모델 파일 | - | 448MB | 113MB |

- ONNX Runtime의 그래프 최적화를 전부 켜면 시작할 때 최대 메모리가 1,047MB였다. 기본 단계만 켜서 805MB (정확도 같음). 메모리 풀(arena)은 거의 차이 없음.
- int8은 곡 설명끼리 정확도가 떨어져(2문장) 쓰지 않는다. EKS에서 메모리가 부족하면 대안 (x86 VNNI용이라 속도는 노드에서 다시 잴 것).
- Python 환경 143MB (PyTorch 환경 797MB).

**실제 곡 41개** (맥북 dev, LLM_MODE=bedrock): 곡 설명 41개(요약 있음 34) 저장, 벡터 40개(근거가 모두 빈 1곡 제외), 54초(지식 캐시), Haiku 25번 약 $0.11, 503 0번. 이웃 예: 뚜두뚜두 → Ditto·Supernova, 밤편지 → 다비치 거북이·안녕이라고 말하지마, 負けないで → 揺れる想い. 어색한 짝도 있음(夜に駆ける → Yellow) → L3-4 점수는 벡터만 쓰지 않는다.

## 11. L3-4 추천과 이유 설계 (2026-10-27 승인)

```
SQS:recommend ─▶ recommend-worker (보강이 끝난 세션에서 시작)
 ① PROFILE  프로필 벡터(들은 곡 벡터의 가중 평균, log(1+재생 수), 고른 곡은 1) + 취향 재료(장르·분위기·가수 상위)
            후보: Last.fm track.getSimilar(상위 곡 10 × 20) + DB 벡터 이웃 30 → 들은 곡·같은 곡 제외 → 사전 점수 상위 50 → rec_candidate
 ② CANDIDATES (5곡씩)  새 후보는 식별 → 지식 인입 → 곡 설명 → 벡터 (기존 코드 재사용)
 ③ RANK  점수 = 0.5 × 프로필 유사도 + 0.3 × Last.fm 유사도 + 0.2 × 같은 작곡가·프로듀서 → 가수당 2곡 → 상위 50
         → LLM 재정렬 20곡 + 이유(근거 청크 인용) + 취향 요약 → 검증(후보·청크 번호) → 모자라면 점수 순으로 채움
```

- **Last.fm 후보는 두 경로** (구현 중 확인, 2026-10-27): track.getSimilar는 한국 곡에서 0곡(아이유·블랙핑크·검정치마), 해외·일본 곡은 30곡(Coldplay·ZARD). artist.getSimilar는 한국 가수도 그럴듯함(아이유 → 태연·볼빨간사춘기·윤하, 검정치마 → 잔나비·혁오). → 비슷한 곡 + **비슷한 가수의 인기곡**(가수 유사도 × 곡 순위 가중).
- 데이터(V13): `taste_profile`, `rec_candidate`, `recommendation` (30일). API `GET /api/sessions/{token}/recommendations`.
- 템포·에너지는 점수에 쓰지 않는다(L3-2: 근거 거의 없음). 가사 언급 금지.
- 모델 비교 Haiku 4.5 vs Sonnet 4.6: 유효 응답률, 이유의 근거 뒷받침(심판), 다양성(서로 다른 가수), 비용·속도, 사람 확인. 비슷하면 Haiku.
- 결정: 가중치 0.5/0.3/0.2로 시작(L3-5 피드백으로 조정), 후보 50 → 추천 20, 가수당 최대 2곡.

## 12. L3-5 피드백과 좋아요 비율

- 목표: 면접 수치 5번 "추천 좋아요 비율"을 이유의 RAG 켬/끔으로 나눠 잰다. 가중치(0.5/0.3/0.2) 조정 근거도 모은다
- 평가: 곡마다 👍/👎, 이유가 있으면 "이유가 틀렸어요" 체크. 다시 누르면 취소
- 비교 방법: 평가자가 적어(본인·지인) 세션 A/B 대신 **한 세션 안 곡 단위 블라인드 섞기**
  - 순위는 RAG 켠 재정렬 그대로. 이유가 있는 곡 중 절반(세션 id로 섞어 고정)을 근거 없이 다시 쓴다(NORAG, Haiku 1회, 입력 약 1.4천 토큰)
  - 근거가 없어 이유를 비운 곡은 비교에서 뺀다 (두 쪽 조건을 같게)
  - 화면은 비교군을 표시하지 않고 출처 링크도 모두 숨긴다 (NORAG는 링크가 없어 구분되므로)
  - 해석: 순위가 같고 이유만 다르므로 "이유가 신뢰·만족에 주는 효과"이지 "추천이 좋아졌다"가 아니다
- 데이터: V14 `recommendation.reason_variant·score_rank·source`, `rec_feedback`(평가할 때 추천 정보를 복사). 세션이 지워지면 `session_id`만 비우고 남긴다(곡·점수·비교군만, 들은 기록 없음)
- API: `PUT|DELETE /api/sessions/{token}/recommendations/{trackId}/feedback`, 추천 조회에 내 평가 포함(비교군은 보내지 않음)
- 집계: `tools/feedback-report/report.sh` — 비교군별 좋아요·이유 틀림 비율, 점수 순위대별(LLM이 끌어올린 곡), 후보 경로별
- 로컬 평가용: `scripts/dev-reissue-link.sh <세션 id>`로 옛 세션 링크를 새로 발급 (DB에는 토큰 해시만 있음)
- 한계: 표본이 작다(세션 1개 = 20곡, 비교군당 10곡). 수치는 "세션 n개, 곡 n개"와 함께 말한다

### 12.x L3-5 첫 측정 (2026-10-27, 세션 15, 평가자 1명, 20곡)

| 비교군 | 평가 | 좋아요 | 이유 틀림 |

| NORAG (근거 없이) | 10 | 8 (80%) | 0 |

- 해석: 1곡 차이는 표본 10곡에서 의미 없음. 이유 틀림이 양쪽 0이라 사람 평가로는 RAG 효과를 가르지 못했다 (Haiku가 근거 없이도 장르·분위기 수준의 안전한 문장을 써서). RAG 효과는 지금까지 L3-2 판정(근거 일치 80% vs 13%)과 L3-4 판정 수치로 말한다
- 점수 순위대: 재정렬 전 1~10위 3곡 100%, 11~20위 7곡 71%, 21위 이하(LLM이 끌어올림) 10곡 70%

- 다음: 평가자·세션을 늘려야 비율 차이를 말할 수 있다. 사람 평가는 "이유 틀림"보다 "이유가 구체적인가"를 묻는 편이 RAG 차이를 볼 수 있을지 검토
