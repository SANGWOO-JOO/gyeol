# 분위기 찾기 개선: Naive RAG → Advanced RAG (검색 전 단계)

11-18 작성. 앞 문서: [vibe-search-rag.md](vibe-search-rag.md) (Naive RAG, 운영 v0.2.1).
상태: 설계 확정 (구현 전). Codex 검수 3회, 3차 "착수 가능" 판정 후 남은 지적 반영.

## 1. 왜 하나

운영(v0.2.1)에서 "비 오는 날 듣기 좋은 노래" → 부활·박효신·Neil Diamond.

- 운영 DB에 태연 「Rain」, 윤하 「빗소리」, 에픽하이 「우산」이 있다 (track 515곡 중 제목에 비 관련 단어 12곡).
- 검색 SQL(`VibeSearch.kt:86-91`)은 `artist_vector`·`artist_profile`만 본다. track은 검색 대상이 아니다.
- 세 가수 설명(LLM 요약)에도 대표곡 제목이 없다. 가수로도 후보 10명에 못 든다.
- 부활 설명의 '비 오는 날의 이야기'는 일본어 위키 「雨とあなたの物語」의 오역 (원제 「비와 당신의 이야기」).
- 박효신 이유의 "비 오는 날 감성"은 근거 밖 연결 (설명은 "허스키한 음성, 발라드").

정리: 생성이 아니라 **검색 단계의 한계** (Gao et al. 2023, Naive RAG의 검색 품질 문제).

## 2. 범위 (1인 프로젝트, 515곡 규모)

| 이번에 함 | 다음 단계로 미룸 | 안 함 |
|---|---|---|
| 0) 근거 번호 소속 검증 (운영 약점) | RRF k·깊이 탐색 (이번엔 k=60 고정) | 가사 수집 (저작권) |
| 1) 데이터 정정 (부활 오역) | 사람 판정 κ (이번엔 일치율·불일치 사례만) | 재순위화, 질문 재작성 |
| 2) 측정 도구 + 기준선 | Last.fm 곡 태그 새 수집 | 원문 청크 직접 색인 |
| 3) 제목 검색 (어휘) → 측정 | | |
| 4) 곡 벡터 (의미) + RRF → 측정 | | |

## 3. 순서

| 단계 | 내용 | 산출 |
|---|---|---|
| 0 | 근거 번호를 그 가수에게 준 번호로만 허용 | 테스트, 배포 |
| 1 | 부활 설명 오역 정정 (해당 가수 설명 재생성, 결과 확인) | 정정된 데이터 |
| 2 | 측정 도구 + **정정 후 데이터로** 기준선 | 기준 수치 |
| 3 | 제목 검색 추가 → 측정 | 어휘 기여 |
| 4 | 곡 벡터 + RRF → 측정 | 의미 기여, 최종 |

데이터 정정을 기준선보다 먼저 해서, 기준선과 개선안이 같은 데이터를 쓴다 (정정 효과가 검색 효과에 섞이지 않게). 지도 판 제한(`VibeSearch.kt:86-91`의 `onMap`)도 양쪽 같은 조건(map_version 0, 전체 카탈로그)으로 잰다.

## 4. 0단계: 근거 번호 소속 검증

현재 `VibeSearchService.kt:175` `allowed = candidates.flatMap { it.evidence }.toSet()` — 후보 10명 근거의 합집합이라, A 가수 이유에 B 가수 번호를 붙여도 통과한다.

- 변경: `VibeGuard.validate`가 `Map<artistId, Set<chunkId>>`를 받아 pick마다 그 가수의 번호만 남긴다. 남은 번호가 0개면 지금처럼 이유 없이 카드만.
- 테스트: 다른 가수 번호만 붙인 pick → 이유 없음.

## 5. 측정 설계 (정답 목록 없음)

사람마다 떠올리는 곡이 다르므로 질문마다 정답 곡을 정하지 않는다. 결과를 기준표로 판정한다.

### 5-1. 질문

- 정상 30개: 날씨 6 · 상황 6 · 감정 6 · 장르/소리 6 · 주제어 직접(비·우산·밤 등) 6.
- 엉뚱한 질문 10개 (음악과 무관, 기존 B안 확인 세트 재사용).
- **튜닝용 / 평가용 분리**: 정상 12 + 엉뚱 4 = 튜닝, 정상 18 + 엉뚱 6 = 평가. 제목 검색 규칙·확장 사전·곡 거리 기준·기준표 문구는 튜닝용으로만 정하고, **평가용을 돌리기 전에 고정**한다. 평가용은 단계마다 한 번씩만 돌린다. 평가용 결과를 보고 규칙을 바꾸면 그 뒤 평가는 "탐색 결과"로 표시한다.

### 5-2. 비교 단위 (주 지표: 첫 화면 결과 효용 P@5)

**질문당 사용자에게 보이는 첫 결과 5개**를 비교한다. 단위(가수/곡)와 무관하게 같은 기준표로 판정한다.
이 지표는 "제품 첫 화면이 얼마나 쓸모 있나"를 잰다. 검색 자체가 낫다는 증명은 아니다 (개선안은 출력 칸이 많아 빈칸 감점을 덜 받는다). 그래서 **출력 개수**와 **실제 출력 중 관련 비율**을 같이 적어 빈칸 효과를 나눠 본다.

- 기준선: 가수 출력(3~5명) 그대로.
- 개선안: 화면 순서대로 곡 카드 → 가수 카드에서 앞 5개 (9절 화면 순서와 같게).
- 결과가 5개보다 적으면 빈 칸은 0점으로 보고 분모 5 고정. **응답률**(결과를 하나라도 낸 정상 질문 비율)을 같이 적는다.
- 보조 지표 (이름을 "보조"로 명시):
  - 검색 후보 단계: 후보 목록 안에 의도 적합 2점이 하나라도 있는가 (기준선은 가수 top-10, 개선안은 곡 top-10 + 가수 top-10).
  - 개선안 곡만의 P@5 (기준선 없음, 단독 보고).
- 곡이 맞았다고 그 가수 전체를 맞은 것으로 보지 않는다 (곡→가수 변환 비교는 하지 않는다).

### 5-3. 판정 (항목 세 개를 따로)

결과 하나(가수 또는 곡)마다:

| 항목 | 값 | 뜻 |
|---|---|---|
| 의도 적합 | 0·1·2 | 이 질문 상황에서 이 결과를 틀어 줄 만한가. 곡은 그 곡, 가수는 "그 가수의 음악을 이 상황에 추천할 만한가". 주제어 유무로 점수를 주지 않는다 |
| 주제어 명시 | 예·아니오 | 제목·설명에 질문 주제가 직접 드러나는가 (어휘 커버리지, 점수 아님) |
| 근거 충실 | 예·아니오·이유 없음 | 이유 문장이 그 결과에 준 근거와 맞는가 |

- 주 지표: 의도 적합 P@5 (2점만 관련 / 1점 이상 관련, 둘 다).
- 보조: 의도 적합 평균, 주제어 명시 비율, 근거 충실 비율 (이유 없음 비율도 따로).
- 엉뚱한 질문: notFound 비율.
- 기존 84%는 "저장된 가수 요약과의 일치도"다 (`tools/vibe-eval/gen_eval.py:118`). 원문 사실성이 아님을 문서·포트폴리오에 적는다.

### 5-4. 편향 줄이기

- **눈가림**: 기준선·개선안 결과의 합집합에서 (질문, 결과 이름, 가수/곡 구분, 저장된 설명 또는 곡 문장)만 주고 의도 적합·주제어 명시를 판정한다. 어느 방식인지·순위·생성 이유는 숨긴다. 근거 충실은 이유가 필요하므로 따로 판정한다.
- 심판 Sonnet, temperature 0, 같은 기준표 문구. 기준표는 튜닝용 판정으로만 고치고 고정.
- 사람 확인: 평가용 판정에서 20개를 질문 유형·점수별로 뽑아 직접 판정, 일치율과 불일치 사례를 기록 (κ는 다음 단계).
- 30문항은 탐색 규모다. 질문별 표를 싣고 "유의" 표현을 쓰지 않는다.
- 평가기 수정: 현 `gen_eval.py`는 이유 없는 결과를 판정·집계에서 뺀다 (`gen_eval.py:166-168`, `:190`). 새 평가기는 이유 없는 결과도 의도 적합을 판정한다.

## 6. 3단계: 제목 검색 (어휘)

`track_search_term`(V6)은 정규화하면서 공백·문장부호를 지운다 (`SearchText.kt:19-20`). 경계 판정이 안 되므로 **원래 제목(`track.title`)** 으로 검사한다. 515곡이라 순차 검색으로 충분하다 (색인 불필요).

- 대상: 곡 제목만 (가수 이름·가수+곡 조합 제외).
- **확장 사전** (파일, 사람이 검수): 주제 → (질문 트리거 단어, 제목 매칭 단어).
  - 예: 비 → 질문 트리거 [비 오는, 비 올, 비가 오, 비 내리, 빗소리, 장마, 우산, rain, rainy], 제목 단어 [비, rain, 빗소리, 우산, 장마, 빗방울, raindrop].
  - **질문 쪽**: 트리거는 두 글자 이상 구로만 둔다. 한 글자 '비'만으로는 발동하지 않는다 ('비교', '비행' 방지). 영어는 단어 경계(`\brain\b`, 'brain' 제외).
  - **제목 쪽**: 한국어는 토큰 경계 기준. 제목을 공백·문장부호로 나눈 토큰이 사전 단어와 **같거나**, 사전 단어 + 조사(가·는·를·와·의·에·이)로만 이루어진 경우만 매칭 ('비가'는 허용, '비가역'·'비밀' 제외). 영어는 소문자 단어 경계.
  - 발동은 한 방향: 질문 트리거 → 제목 단어. 제목 단어로 질문을 해석하지 않는다.
  - 부정 표현: 트리거 앞뒤 6글자 안에 "말고·빼고·제외·아닌"이 있으면 그 주제는 발동하지 않는다. 완전한 부정 해석이 아닌 제한적 규칙이다 ("비 오는 날 말고 밤 노래"에서 근처 다른 주제까지 막을 수 있음). 튜닝 사례로 고정한다.
- 순위: 서로 다른 매칭 사전 단어 수 (별칭 중복 제외) → `plays_total` 내림 → track.id 오름.
- 확장 사전은 튜닝용 질문에 나오는 주제만 최소로 만든다 (평가용을 보고 추가하지 않음).

## 7. 4단계: 곡 벡터 (의미)

- 새 테이블 `track_vibe_vector(track_id PK, embedding vector(384), model, text_hash, created_at)`. 기존 `track_vector`(V12)는 곡 설명 전용 한 행이고 `query` 접두어로 만들어져 있어 (`EmbedClient.kt:26-31`) 건드리지 않는다.
- 문장: `제목 · 가수` + (있으면) 곡 설명 중 **곡·음반 수준이고 신뢰도 MEDIUM 이상인 칸**만. `descriptorText`(`VectorRepository.kt:24-29`)는 ARTIST 수준·LOW도 넣으므로 새 함수로 걸러 쓴다.
- 곡 설명 없는 곡은 `제목 · 가수`만. 가수 설명을 곡 문장에 복사하지 않는다.
- 접두어: 문서 `passage:`, 질문 `query:`. `text_hash`는 `모델 + 접두어 + 본문`으로 만든다 (모델·접두어가 바뀌면 재색인).
- 515곡 1회, 로컬 embed 서비스 (비용 없음).

## 8. 합치기와 notFound

- 곡 후보: 제목 검색 목록 + 곡 벡터 top-10을 RRF로 합친다. `score = Σ 1/(60 + rank)`, 없는 목록 항은 0, 곡 ID로 병합, 동점은 track.id. 곡 벡터는 거리 기준(튜닝용으로 결정) 밖이면 목록에서 뺀다.
- 가수 후보: 지금처럼 가수 설명 벡터 top-10. 거리 0.22는 **top-1만 보는 게이트**(`VibeSearchService.kt:157`)로 유지한다. 통과하면 0.22 밖 후보도 그대로 넘긴다 (기준선과 같은 동작).
- LLM 입력: 곡 후보 ≤10, 가수 후보 ≤10을 **따로** 주고 "곡 0~5, 가수 0~3"을 고르게 한다. 질문이 음악과 무관하면 둘 다 빈 배열 (현 B안 규칙 유지, `VibeSearchService.kt:169-176`).
- 근거: 곡은 7절에 쓴 descriptor 칸의 evidence, 제목 일치 곡은 '제목 일치'를 근거로 표시 (청크 번호 없음). 0단계와 같이 근거 번호는 그 곡·가수 소속만 허용.
- **notFound 규칙** (최종 출력 기준):
  1. 곡 후보와 가수 후보가 모두 비면 LLM 없이 notFound.
  2. 실제 LLM이 곡·가수 모두 빈 배열이면 notFound (제목 일치 곡이 있어도 채우지 않는다 → 음악과 무관한 질문이 제목 일치로 통과하지 않게).
  3. LLM 실패(예외)면: 제목 일치 곡이 있으면 그 곡을 이유 없이 최대 3개, 없으면 지금처럼 가수 상위를 이유 없이.
  4. 검증 뒤 둘 다 0개면 notFound.
  - 최소 개수 자동 채우기(`VibeSearchService.kt:116`의 minPicks 보충)는 **LLM 예외(3번)일 때만** 쓴다. 정상 응답에서 LLM이 고른 수가 적으면 채우지 않는다.
- 엉뚱한 질문 notFound 비율이 기준선(10/10)보다 떨어지면 실패로 본다.

## 9. 화면·API

- `VibeSearchView`에 `tracks[{trackId, title, artistName, reason|null, titleMatch, evidence, inRoomBy}]` 추가, 기존 `picks`(가수)는 그대로.
- 화면 순서: 곡 카드(바로 "담기") → 가수 카드. 5-2의 "첫 5개"는 이 순서.
- **결과 버전**: `vibe_search`에 `algo_version` 칸 추가, 재사용 키(`VibeSearch.kt:53`)에 넣는다. 배포 필수 (안 넣으면 개선 전 결과를 재사용).

## 10. 끝났다고 볼 조건

- 0단계 테스트 통과, 배포.
- 평가용 18문항에서 첫 5개 의도 적합 P@5가 기준선보다 높고, 근거 충실 비율이 떨어지지 않음.
- 엉뚱한 질문 평가용 6개 notFound 유지.
- 주제어 질문에서 제목 일치 곡이 첫 5개에 드는 비율 보고 (어휘 커버리지, 성공 조건 아님).
- 사람 판정 20개 일치율과 불일치 사례 기록.

## 11. 비용 (추정)
