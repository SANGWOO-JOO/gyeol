# ⓪ 노래 담기 경로 측정과 P0 (2026-11-13)

음악 방 구현 순서 ⓪ (`room-api-db.md` 6절). 방에서 "담기"를 누른 뒤의 흐름(식별 → 근거 보강 → 곡 설명 → 벡터)은 지금 곡 고르기 파이프라인과 같으므로 그것으로 쟀다.

## 1. 방법

- 스크립트: `tools/measure-add/measure.mjs`, 원자료: `tools/results/measure-add.json`
- 로컬(맥북), api·worker·fetcher·embed, **LLM_MODE=bedrock**(Haiku 4.5). worker는 추천 큐를 빼고 띄움(추천 20곡 후보 보강 비용 방지).
- 곡 고르기 세션에 3곡을 넣고 1초마다 상태를 읽음. 시간은 곡 저장 요청부터.
  - 식별 끝: 식별 대상이 모두 끝남(DB 곡만이면 대상 없음)
  - 준비 끝: 보강 대상이 모두 끝남(근거 수집·곡 설명·벡터 포함)
- 시험 4가지 × 3회. 회차마다 다른 곡(한 번 넣은 곡은 DB에 남아 빨라짐).
  - ① DB 곡 3 (벡터까지 있는 곡)
  - ② DB 2 + Last.fm 1
  - ③ Last.fm 3 (DB에 없는 한·일 인기곡)
  - ④ 식별이 안 될 곡 3 (커버·연주·플레이리스트 영상 제목, 없는 곡)
- 1초 간격으로 읽어서 시간은 ±1초.

## 2. 결과 (1회 측정, 표본 작음)

| 시험 | 식별 성공 | 식별 끝 (중앙값 / 최대) | 준비 끝 (중앙값 / 최대) |
|---|---|---|---|
| ① DB 3 | 9/9 (식별 불필요) | – | **1.0초** / 3.3초 |
| ② DB 2 + Last.fm 1 | Last.fm 3/3 | 2.0초 / 2.1초 | **13.1초** / 13.2초 |
| ③ Last.fm 3 | 9/9 | 6.1초 / **81.7초** | **40.4초** / 115.0초 |
| ④ 실패 3 | 0/9 (기대대로) | 9.1초 / 12.2초 | – (보강 없음) |

- 실제 곡(Last.fm에서 고른 12곡)은 모두 식별됨. ④는 LLM 제목 정리까지 거친 뒤 실패로 끝남.
- ③ 2회차 식별 81.7초: "BTS - Spring Day"가 LLM 표기 후보(방탄소년단 / 봄날)를 거쳐 MusicBrainz를 여러 번 찾은 묶음. 원인 세부는 확인하지 않음(초당 1회 제한 + 후보 수로 추정).
- 준비 시간 대부분은 근거 수집(MusicBrainz·Wikipedia·Last.fm, 곡당 대상 약 4개)과 곡 설명(Bedrock 1.4~3.2초/호출).
- Bedrock 사용(측정 전체): 곡 설명 10회(13곡) 입력 23,387·출력 2,470 토큰, 제목 정리 7회 입력 9,532·출력 738 토큰. Haiku 4.5 단가(입력 $1·출력 $5 / 100만 토큰, 확인 안 한 공개 단가 기준)로 **약 $0.05 추정**.

## 3. 방 설계에 주는 뜻

| 화면 | 기대 시간 | 처리 |
|---|---|---|
| DB에 있는 곡 담기 | 1초 안팎 | 바로 위성 (201) |
| DB에 없는 곡 담기 | 식별 2~6초, 준비 10~40초 (가끔 1~2분) | 위성은 식별이 끝나면 바로 띄우고, 곡 설명·벡터는 뒤에서. 4-g "준비 중"은 **새 가수**일 때만(아래) |
| 못 찾는 곡 | 8~12초 뒤 판정 | 4-i까지 약 10초. 그동안 "찾는 중" 표시 필요 |

- 지도에 점을 찍는 데 필요한 것은 track_id와 가수 좌표뿐. 곡 설명·벡터는 놀이터·행성 판 설명용이라 기다릴 필요 없음 → `room_song`은 식별 직후 저장.
- 새 가수 좌표(artist-prepare: 가수 근거·설명·벡터)는 측정하지 않음(아직 없음). 곡 보강과 비슷한 10~40초로 추정 → 4-g "준비 중"이 실제로 뜨는 경우.
- 식별 지연(최대 81초)을 줄이는 일은 첫 배포 범위 밖. 방에서는 1인 동시 3개 제한으로 막힘을 막는다.

## 4. P0 수정 (기존 곡 고르기 → 추천 흐름)

| 문제 | 원인 | 수정 |
|---|---|---|
| 고른 곡을 하나도 못 찾으면 "준비 중"에서 멈춤 | 보강 대상이 0곡이라 추천이 시작되지 않고 상태가 NONE에 머묾 | 추천 API가 고른 곡 식별이 끝났는데 찾은 곡이 0이면 `EMPTY`를 돌려줌. 웹은 기다리기를 멈추고 "영어 제목이나 원래 제목으로 다시 골라 보세요" 안내 |
| 식별 실패 곡이 조용히 빠짐 | 추천은 track_id가 있는 곡만 읽음 | 추천 응답에 `unidentified`(찾지 못해 빠진 곡 수)를 넣고 결과 위에 "고른 곡 중 N곡은 찾지 못해 빼고 골랐어요" |

- 코드: `RecommendRepository.seedStatus`, `RecommendController`, `web/src/api.ts`, `web/src/pages/Result.tsx`
- 테스트: `SessionApiIntegrationTest` "추천 상태 - …" (식별 중 NONE → 0곡 EMPTY·3 → 1곡 찾으면 NONE → 추천 저장 후 READY·2). 측정 ④ 세션에서도 실제로 `EMPTY`, `unidentified 3` 확인.
