# 코드 맞추기 이유: 벡터 검색으로 근거 고르기 (설계, 11-18)

상태: **11-18 구현·측정 완료** (D1~D5 제안대로. D3은 측정 전까지 `gyeol.worker.code-match.max-pair-distance` 기본 1.0 = 거르지 않음)

## 1. 목적

코드 맞추기 이유(RAG 2)를 "임베딩 → 벡터 검색 → 근거 첨부 → 생성 → 검증" 흐름으로 바꾼다.
지금은 근거로 붙일 가수를 **겹친 가수, 없으면 각자 많이 담은 가수**로 고른다. 겹친 가수가 없는 두 사람은
서로 관계없는 가수 설명만 받게 되어, 이유가 "각자 이런 걸 들어요"로 끝나거나 근거 번호를 못 달아 버려진다.
두 사람 가수 중 **벡터가 가까운 짝**을 찾아 붙이면 "A의 X와 B의 Y가 둘 다 …" 같은 연결 근거가 생긴다.

## 2. 지금 동작 (코드 기준)

- `CodeMatchReasonService` (worker/codematch): 겹친 가수 `shared`, 없으면 각자 많이 담은 가수 2명씩(`top`) → 최대 6명
- `CodeMatchRepository.artistEvidence(ids)`: 설명과 근거 번호가 있는 가수만 가져옴
- `BedrockCodeMatchLlm.reason`: 닉네임·점수·겹친 구역·겹친 가수 + 가수 설명 `[번호]`를 넘기고, 허용한 번호만 남김. 번호가 없으면 이유 없음
- 벡터: `artist_vector.mixed`(원문 0.5 + 설명 0.5), `raw`(원문만). HNSW 인덱스는 `mixed`에 있음 (`V23__artist_map.sql:30`)

## 3. 바뀌는 동작

```
두 사람의 가수 집합 A, B
 ├─ 겹친 가수가 있으면 먼저 근거 후보로 (거리 0으로 취급)
 ├─ A의 가수 a마다 B의 가수 중 코사인 거리가 가장 가까운 b를 찾음 (B→A도 같게)
 ├─ 짝을 거리순으로 정렬, 거리 기준(T)보다 먼 짝은 버림
 ├─ 상위 짝 N개의 두 가수 설명·근거 번호를 붙임 (가수 최대 6명은 그대로)
 └─ 프롬프트에 "가까운 짝: X(A) ↔ Y(B)"를 알려 주고, 생성·검증은 지금과 같음
```

쿼리 (`CodeMatchRepository.nearestPairs`, 설명·근거 번호가 있는 가수만):

```sql
-- A의 가수마다 B 안에서 가장 가까운 가수 1명 (설명 있는 가수만)
SELECT a.artist_id AS a_id, nb.artist_id AS b_id, nb.d
FROM artist_vector a
CROSS JOIN LATERAL (
  SELECT b.artist_id, b.mixed <=> a.mixed AS d
  FROM artist_vector b
  WHERE b.artist_id = ANY(:bIds) AND b.artist_id <> a.artist_id
  ORDER BY d LIMIT 1
) nb
WHERE a.artist_id = ANY(:aIds)
ORDER BY nb.d LIMIT :n
```

- 한 사람의 가수는 많아야 수백 명이라 **후보 집합 안에서 정확 검색**(전수 비교)이 된다. HNSW는 전체 가수 대상 검색용이라 여기서는 쓰이지 않을 수 있다. 포트폴리오에는 "pgvector 코사인 거리로 두 사람 가수 사이 가장 가까운 짝 검색"으로 쓰고, HNSW를 썼다고 쓰지 않는다.

## 4. 그대로 두는 것

점수 계산(`CodeMatch.parts`/`score`), 결과 캐시 조건, 프롬프트의 근거 번호 규칙, 번호 검증, 실패 큐 → 이유 없이 완료, 가짜 모드

## 5. 정할 것

| # | 항목 | 후보 | 제안 |
|---|---|---|---|
| D1 | 비교할 벡터 | `mixed` / `raw` | `mixed`. 단 설명 없는 가수는 근거가 없어 어차피 빠지므로 섞임 문제(지도 판 4)는 생기지 않음 |
| D2 | 붙일 짝 수 N | 2 / 3 / 4 | 3 (가수 최대 6명 유지) |
| D3 | 거리 기준 T | 없음 / 측정 후 정함 | 측정 표본에서 Last.fm 유사 짝의 거리 분포를 보고 정함 (예: 하위 50%) |
| D4 | 겹친 가수와의 관계 | 겹친 가수 우선 + 남은 자리에 짝 / 짝만 | **(측정 뒤 변경) 겹친 가수가 있으면 겹친 가수만, 없을 때만 벡터 짝** |
| D5 | 프롬프트에 짝 표시 | 표시 / 안 함 | 표시 ("가까운 짝: X ↔ Y") |

## 6. 테스트

- 겹친 가수만 있음 / 겹친 가수 없음 / 둘 다 있음
- 벡터가 없는(자리 없는) 가수가 섞임 → 짝 후보에서 빠짐
- 거리 기준보다 먼 짝만 있음 → 지금 방식(많이 담은 가수)으로 돌아감
- 가짜 모드 결과가 바뀌지 않음 (기존 테스트 유지)

## 7. 측정 (Bedrock 약 $1, 실행 전 확인)

- 표본: 로컬 지도 가수로 만든 가상의 두 사람 30쌍 (겹친 가수 없음 15쌍 · 있음 15쌍), 고정 시드
- 비교: 지금 방식 vs 벡터 짝 방식, 같은 Haiku·같은 프롬프트
- 지표
  - 이유가 나온 비율 (번호 검증 통과)
  - 이유 문장의 근거 충실도 (Sonnet 심판, `tools/artist-eval`과 같은 문장 단위 판정)
  - 겹친 가수 없음 쌍에서 "두 사람을 잇는" 문장 비율 (심판 판정)
- 도구: `tools/codematch-eval/` (새로 작성)

## 8. 포트폴리오 반영 (측정 뒤)

- 16쪽, `docs/images/pipeline.png` ②: 점수 계산 → **임베딩 짝 검색(pgvector)** → 생성 → 출력 검증, 전후 수치
- 14쪽 주석의 "벡터 검색은 지도 이웃" 문구 정리

## 9. 하지 않는 것

- 가수 설명(RAG 1)의 근거를 이웃 가수 청크로 채우지 않는다 (다른 가수 사실이 섞여 환각)
- 점수 계산에 LLM을 넣지 않는다

## 10. 측정 결과 (11-18, 로컬, 30쌍: 겹침 없음 15 · 있음 15, 같은 표본 3회)

`tools/codematch-eval/eval.py`, 결과 `tools/results/codematch-eval-v2r{1,2,3}.json` (1차 `-v1`은 프롬프트 수정 전이라 비교에서 뺌)

| 구분 | 근거로 뒷받침되는 문장 (3회 합) | 근거와 어긋난 문장 (회차별) | 두 사람을 잇는 이유 (회차별) |
|---|---|---|---|
| 겹침 없음: 전 → 후 | 45% → **57%** | 10·10·10 → 1·1·3 | 3·4·4 → 8·6·7 |
| 겹침 있음: 전 → 후 | 84% → 83% | 0·0·0 → 3·3·3 | 10·10·10 → 8·8·7 |

- 1차(프롬프트 수정 전): 짝을 "둘 다 좋아한다"로 써서 어긋난 문장이 늘었다 → 시스템 프롬프트에 "짝은 서로 다른 가수, 함께 좋아한다고 쓰지 말 것" 추가
- 겹친 가수가 있을 때 짝을 섞으면 잡음이 되어 D4를 바꿨다: 겹침 있음 = 기존 동작, 겹침 없음 = 벡터 짝
- 짝 거리(코사인)는 0.051~0.089로 몰려 있어 거리 기준(D3)은 두지 않음 (기본 1.0 유지)
- Haiku 토큰이 3회 거의 같아 생성은 사실상 고정, 흔들림은 주로 심판(Sonnet) 판정. 비용 회당 약 $0.85, 이 기능 측정 합계 약 $3.5 (추정)
