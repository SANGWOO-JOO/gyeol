# 청취 분석의 레이턴시·오류 개선

추천보다 청취 분석(많이 들은 곡·가수·언제 들었나)을 먼저 빠르고 오류 없이 만든다. k3d 검증은 이 작업 뒤에 한다.
공개 저장소이므로 실제 곡 목록은 적지 않고 패턴과 건수만 적는다.

상태: 1~7번과 방송 영상 가수 뽑기 완료, 전체 재측정 완료 (2026-11-09)

## 최종 재측정 뒤 추가 수정 (2026-11-09)

흔한 이름의 가수는 필드 검색 상위 10명에 실제 가수가 없어, 이름이 같은 다른 가수의 곡만 찾다 실패했다. 곡을 못 찾으면 넓은 검색으로 이름이 정확히 같은 후보를 한 번 더 본다. 못 찾은 규칙 경로 25곡을 다시 호출해 7곡(재생 387회)을 새로 찾았고, 정답 세트는 변화 없다 (37곡 찾음, 29곡 중 28곡 일치). 전체 시간과 식별 비율은 아래 표에 반영되어 있지 않다.

방송 영상 가수·곡 뽑기: 식별 뒤 `guess` 큐에서 일반 채널 영상(5회 이상, 세션당 최대 500개)을 LLM으로 읽어 `title_guess`에 저장하고, 이 세션에서 확인된 가수일 때만 순위에 더한다. 곡까지 일치하면 곡 순위에도 더하고, 커버는 가수에만 더한다.

- 시험(영상 257개, 재생 2,717회, Haiku 4.5): 66초, 약 0.14달러 (10개씩 순차 호출).
- 재측정 세션 결과: 제외 재생 3,259회 → 1,825회. 곡 확인 비율(MusicBrainz 기준)은 그대로다.
- 반영 대상을 사람이 읽어 본 결과 틀린 가수는 소수였다 (정답 세트 측정 아님).
- 괄호 규칙은 이번 시험에서 거른 것이 없다. 비용이 없는 안전장치로 둔다.

## 원인

### A. 오류 31곡: 검색 페이지 한도 초과 (확인됨)

- MusicBrainz 검색은 `offset + limit`이 500을 넘으면 400을 돌려준다. 녹음 628개인 가수로 직접 호출해 확인했다 (offset 400은 200, 500은 400).
- `MusicBrainzIdentifier.scanArtist`는 최대 offset 900까지 훑는다. 녹음이 500개를 넘는 가수에서 제목을 못 찾으면 항상 400이 난다.
- `MusicBrainzClient.fetch`는 400을 `UpstreamException`으로 던지고, fetcher는 503으로 응답하며, `IdentifyService.process`는 예외로 끝나 메시지 전체를 다시 받는다.
- 같은 곡에서 같은 400이 나므로 3번 재시도 후 실패 큐로 간다. 실패는 메시지 4개(6·10·9·6곡)이고, 원인 곡 뒤의 곡은 시도조차 못 한다.
- 오류 곡 8개 표본을 다시 호출한 결과: 찾음 5, 못 찾음 2, 400 재발 1. 대부분 무고한 곡이었다.

### B. 못 찾은 곡의 큰 몫: 괄호 병기 제목 비교 (확인됨)

- `TitleMatch.sameTitle(candidate, wanted)`는 MusicBrainz 쪽 제목만 괄호·`/`로 나누고, 찾는 제목은 전체를 그대로 비교한다.
- 그래서 `영문 (한글)`, `제목 (제목)`, `제목 (Feat. 가수)` 형태의 Topic 채널 제목이 실패한다.
- 규칙 방식 못 찾음 89곡 중 61곡(재생 3,897회, 12.5%)이 괄호를 포함한다. 한글+괄호 Topic 제목은 찾음 5곡, 못 찾음 52곡이었다.
- 괄호를 뺀 제목으로 호출한 표본 4개는 4개 모두 호출 2번으로 찾았다 (기존 6번 이상 호출 후 실패).

### C. 그 밖의 못 찾음 (일부만 확인)

- 곡 없음·음반 조건 불일치: 괄호 없는 28곡. 가수 표기(로마자 Topic 채널), 해당 가수로 등록되지 않은 곡, 공식 음반 조건 등이 섞여 있다. A·B 수정 후 남은 건을 다시 나눈다.
- LLM 경유 못 찾음 10곡 안팎: 방송 영상 제목. 가수·곡 분리가 잘못된 건도 1건 있었다.
- 메들리·연주곡·곡 아님 등 판정 6곡은 식별하지 않는 것이 맞다.

### D. 화면

- 처리 순서: 메시지는 재생 순으로 보내지만 표준 SQS는 순서를 보장하지 않고 2개씩 동시에 처리한다. 재시도까지 겹쳐 상위 곡이 늦게 채워진다.
- 가수 순위: 식별된 곡은 원곡 가수로, 안 된 곡은 채널명으로 집계돼 같은 가수가 두 줄로 나오고 방송 채널이 순위에 오른다.
- 업로드 미리보기 기간은 YouTube 판정으로 추가된 기록을 반영하지 않아 결과 화면 기간과 다르다.

## 수정 설계 (구현 전, 순서대로)

| # | 변경 | 기대 효과 | 위치 |
|---|---|---|---|
| 1 | 훑기 범위를 `offset + limit <= 500`으로 제한 | 400 재발 방지 | `MusicBrainzIdentifier.scanArtist`, `recordings` 페이지 범위 확인 |
| 2 | 곡 하나의 영구 실패가 묶음을 망치지 않게 함 (4xx는 재시도하지 않고 그 곡만 `FAILED`) | 오류 전파·재시도 시간 제거 | `MusicBrainzClient.fetch`, fetcher 응답, `IdentifyService.process` |
| 3 | 찾는 제목도 괄호·`/` 부분으로 나눠 비교. `feat.`, `Bonus Track` 등 곡명이 아닌 부분은 제외하고, 검색어도 앞부분 기준으로 먼저 시도 | 식별 증가, 호출 감소 | `TitleMatch`, `MusicBrainzIdentifier.recordings` |
| 4 | 남은 못 찾음 재분류 후 훑기 조건 줄이기 | 호출 감소 | A~C 재측정 뒤 결정 |
| 5 | 상위 곡 우선 처리 | 체감 레이턴시 | 작은 첫 묶음 또는 메시지 구성 |
| 6 | Topic 채널을 식별된 가수에 합치기, 방송 채널 분리 | 순위 정확도 | `StatsService.topArtists` |
| 7 | 식별 뒤 보강·추천 자동 실행을 설정으로 끄기 | 측정 분리, 비용 절약 | `EnrichTrigger` |

3번은 오답을 늘릴 수 있다 (같은 가수의 짧은 제목이 부분 일치). 기존 정답 세트(`tools/identify-eval`, 28/29)와 단위 테스트로 회귀를 확인한다.

기대치: A·B만으로 재생 기준 식별 비율의 상한은 약 50% (32.0 + 12.5 + 6.1). 시간 목표는 1~3번 뒤 재측정해서 정한다.

## 재측정 방법

1. 같은 Takeout을 사용한다. 파일은 저장소에 넣지 않는다.
2. 전역 캐시(`title_alias`, `track` 등) 때문에 그대로 다시 올리면 빨라 보이고 못 찾음이 30일간 재시도되지 않는다. 비교 전에 로컬 캐시를 비운다 (사용자 확인 후).
3. 기준선 표의 항목을 같은 방식으로 다시 잰다.
