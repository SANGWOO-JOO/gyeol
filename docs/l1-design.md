# L1 설계: 로컬 백엔드 골격과 두 입구

- 작성일: 2026-10-20
- 상태: 승인 (2026-10-24, 10장 결정 완료)
- 상위 문서: `docs/design-v3.md` (내용은 v4) 12장 일정의 L1

L1의 목표는 **로컬에서 두 입구가 처음부터 끝까지 동작하는 것**이다. 곡 식별, LLM, 추천은 L2·L3에서 하고, L1은 그 앞까지만 만든다. AWS 비용은 0이다.

---

## 1. 범위

| 포함 (L1) | 제외 (다음 단계) |
|---|---|
| 백엔드 골격 (모듈, DB, 큐, 설정) | YouTube API로 음악인지 판정 → L2 |
| A 입구: 곡 검색, 3~5곡 선택·저장 | 곡 식별, LLM 제목 정리 → L2 |
| B 입구: 브라우저 필터 → 업로드 → 큐 → 저장 | RAG, 임베딩, 추천 → L3 |
| 기본 통계 (제목·채널 단위) | KEDA 확장 측정, AWS 배포 → EKS 회차 |
| 세션 토큰 링크, 즉시 삭제 | 만료 데이터 자동 삭제 작업 → L2 |
| 가상 Takeout 생성기 (실제 파일이 오기 전 개발용) | |

## 2. 흐름

**A. 곡 고르기**

```
검색어 입력 (0.5초 멈추면 검색)
 → api: 우리 DB 먼저 검색
 → 없으면 external-fetcher → MusicBrainz (초당 1회 제한)
 → 3~5곡 선택 → seed_track 저장 → 결과 링크 /r/:token
```

**B. 청취 기록 업로드**

```
브라우저 (Web Worker)
 1. watch-history.json 읽기
 2. 규칙 필터: 유튜브 뮤직 앱 기록, " - Topic" 채널, 삭제된 영상 제외
 3. 미리보기: 전체 N건 / 음악 M건 / 미판정 K건   ← 미판정은 L1에선 버림
 4. 음악 항목만 JSON으로 묶음 → 서명 URL로 S3에 직접 업로드
                                    │ S3 업로드 이벤트
                                    ▼
 SQS:parse → parse-worker → listen_event 저장 → 세션 상태 "완료"
                                    ▼
 결과 화면 /r/:token → 기본 통계
```

- 일반 영상 제목은 서버로 보내지 않는다. L1에서는 미판정 항목도 보내지 않는다.

**실제 파일로 확인한 형식 (2026-10-24, 한국어 설정 계정 1개, 내용은 기록하지 않고 구조·건수만)**

| 항목 | 확인 결과 | 필터·파서에 반영할 것 |
|---|---|---|
| 파일 | `Takeout/YouTube 및 YouTube Music/시청 기록/시청 기록.json` (약 15MB). 같은 폴더에 `검색 기록.json`도 옴 | 파일 이름이 언어마다 다름 → 이름이 아니라 **내용 구조로 판별**. 검색 기록 파일은 거절 |
| 최상위 | 배열, 30,500건, 기간 2026-03-19 ~ 2026-10-24 | 5만 건 가상 파일로 시험하면 충분 |
| 필드 | `header`, `title`, `titleUrl`, `subtitles`(채널), `time`, `products`, `activityControls` (일부 `description`) | 쓰는 것은 header·title·titleUrl·subtitles·time |
| header | `YouTube` 24,615 / `YouTube Music` 5,885 (뮤직 앱은 `music.youtube.com` 주소) | 출처 판별은 header 또는 주소 도메인 |
| title 형식 | 한국어: `…을(를) 시청했습니다.` 28,332건. 그 밖에 `… 목록을 확인함`, `… 제작 도구 사용함` 같은 **시청이 아닌 활동** 2,168건 | 언어별 시청 문구(`…을(를) 시청했습니다.`, `Watched …`)를 떼어 제목을 얻고, 시청 문구가 없는 활동은 제외 |
| 삭제·비공개 영상 | 주소·채널 없음 28건, 제목이 URL인 것 5건, 채널 없음 528건 | 제외 |
| 규칙 필터 결과 | 뮤직 앱 또는 `" - Topic"` 채널 6,994건(23%). 고유 영상 20,904개 중 규칙에 안 걸린 것 19,015개 | L1 통계는 음악의 일부만 반영함을 화면에 표시(미판정 건수). 일반 유튜브의 뮤직비디오·공식 채널은 L2의 YouTube API 판정이 필요(19,015개 ÷ 50 ≈ 381 유닛, 하루 한도 1만 안) |

- 가상 Takeout 생성기는 이 구조(한국어 문구, 시청이 아닌 활동, 삭제 영상, 뮤직 앱 약 20%)를 따른다.

**같은 설정으로 두 번 내보낸 결과 (2026-10-24, 같은 계정, 38분 간격)**

| 내보내기 | 건수 | 기간 |
|---|---|---|
| 1차 (18:44 요청) | 30,500 | 2026-03-19 ~ 10-24 |
| 2차 (19:22 요청) | 10,900 | 2026-08-06 ~ 10-24 |

- 계정의 YouTube 기록 화면에는 3월 19일 이전 기록도 있다. 즉 **Takeout은 최근 기록부터 일부만, 그것도 내보낼 때마다 다른 양을 준다.** 두 파일 모두 끝 시각은 같고 시작만 다르며, 건수가 100 단위로 끝난다(원인은 확인하지 못함).
- 반영할 것
  - 결과 화면에 **실제 분석 기간과 건수**를 반드시 보여 준다("3월 19일 ~ 10월 24일, 30,500건").
  - 기간이 짧으면 "다시 내보내면 더 많이 올 수 있다"고 안내한다. 사용자 안내 문서 FAQ에 반영.
  - 같은 사용자가 여러 파일을 올리면 시각+영상 주소로 중복을 제거해 합친다(L2 이후 선택 기능).
**형식·출처를 바꿔 세 번째로 내보낸 결과 (2026-10-24 19:41 요청, 같은 계정)**

| 출처 · 형식 | 파일 | 시청 항목 | 가장 오래된 시청 |
|---|---|---|---|
| YouTube 및 YouTube Music → 시청 기록 · JSON (1차) | `시청 기록.json` 15MB | 28,332 (전체 30,500) | 2026-03-19 |
| YouTube 및 YouTube Music → 시청 기록 · **HTML** | `시청 기록.html` 49MB | 40,444 (전체 43,400) | 2025-11-28 |
| 내 활동 → YouTube · HTML | `내 활동/YouTube/내활동.html` 123MB | 95,493 (전체 110,669, 검색 8,562 포함) | 2023-03-11 |
| **내 활동 → YouTube · JSON** (20:28 요청) | `내 활동/YouTube/내활동.json` **51MB** | **95,681** (전체 111,025, 검색 8,639·기타 6,705 포함) | **2023-03-11** |

**결정 (2026-10-24): 입력은 "내 활동 → YouTube · JSON" 하나로 한다.**
- HTML과 기간·건수가 같다(차이는 두 내보내기 사이에 생긴 활동). 잘리지 않는다.
- 필드 구조가 "YouTube 및 YouTube Music" JSON과 같다(`header`, `title`, `titleUrl`, `subtitles`, `time`, `products`, `activityControls`). **HTML 파서는 만들지 않는다.**
- 51MB라 데스크톱 브라우저에서 한 번에 읽을 수 있다. 모바일은 L1 범위 밖.
- 필터는 제목 끝 문구로 시청(`…을(를) 시청했습니다.` / `Watched …`)만 남기고 검색(`…을(를) 검색했습니다.`)과 기타 활동을 버린다. **검색 기록은 서버로 보내지 않는다.**
- "YouTube 및 YouTube Music"으로 받은 파일도 같은 구조라 그대로 읽히지만, 짧다는 안내를 띄운다.

**채택한 파일의 내용 (내 활동 → YouTube · JSON, 계정 1개, 제목은 보지 않고 개수만)**

| 항목 | 값 |
|---|---|
| 전체 항목 | 111,025 = 시청 95,681 + 검색 8,639 + 기타 6,705 |
| 기타 활동 끝 문구 | `목록을 확인함` 5,817 / `채널을 구독했습니다.` 255 / `게시물을 조회함` 97 / 공유된 동영상 92 / `도구 사용함` 40 |
| 시청 기간 | 2023-03-11 ~ 2026-10-24 (약 3년 7개월), 기록 있는 날 1,268일, 하루 평균 75건 |
| 연도별 시청 | 2023년 1,534 / 2024년 9,982 / 2025년 46,911 / 2026년 37,254 (10월까지) |
| 출처 | 뮤직 앱 20,811 (22%) / 일반 앱 74,870 |
| 채널 없는 시청 (삭제·비공개 추정) | 4,305 → 제외 |
| L1 규칙 필터 (뮤직 앱 또는 `- Topic` 채널) | **25,409건 (시청의 27%), 고유 영상 4,628개** → 곡당 평균 5.5회 재생 |
| 규칙에 안 걸린 고유 영상 | 52,494개 → L2 YouTube API 판정 약 1,050유닛 (하루 한도 1만 안) |

- 쓰임: 가상 Takeout 생성기의 비율(시청·검색·기타, 뮤직 앱 비율, 반복 재생)을 이 값에 맞춘다. 부하 실험에도 실제 규모(시청 약 10만 건)를 기준으로 삼는다.

- **"내 활동"으로 받은 YouTube 기록이 압도적으로 길다(약 3년 7개월).** 건수도 100 단위로 끊기지 않아, 잘림 없이 온 것으로 보인다. "YouTube 및 YouTube Music" 쪽은 JSON이든 HTML이든 최근 일부만 온다(HTML이 조금 더 길 뿐).
- 내 활동 파일에는 **검색 기록과 기타 활동이 섞여 있다.** 브라우저 필터가 시청 항목만 남기고, 검색 기록은 절대 서버로 보내지 않는다.
- HTML 본문 형식(한국어): `<a href="…watch?v=ID">제목</a> 을(를) 시청했습니다.<br><a href="…channel/ID">채널</a><br>2026. 10. 24. 오후 6:28:26 KST<br>`. 출처는 각 항목의 머리 칸(`YouTube` / `YouTube Music`)에 있다.
- (위 결정으로 정리됨) 내 활동을 JSON으로 받아도 잘리지 않아, HTML 조각 파서는 필요 없어졌다.

- **macOS의 한글 파일 이름은 자모가 분해된 형태(NFD)**로 저장된다. 파일 이름을 비교할 일이 있으면 NFC로 정규화한다. 판별은 원래대로 이름이 아니라 내용 구조로 한다.

## 3. 모듈

| 모듈 | L1에서 하는 일 |
|---|---|
| `backend/core` | 도메인 모델, 공통 설정, DB 접근 |
| `backend/api` | REST API, 서명 URL 발급, 통계 조회 |
| `backend/worker` | parse 역할만 (역할은 환경 변수로 지정) |
| `backend/external-fetcher` | MusicBrainz 검색만, 초당 1회 제한, 내부 HTTP로 api에 제공 |
| `web/` | 입구 선택, 곡 고르기, 업로드(Web Worker 필터), 결과·통계 화면 |
| `tools/fake-takeout` | 가상 청취 기록 생성기 (예: 5만 건, 음악·일반 영상 섞음) |

- `mcp-server`는 L4에서 만든다.

## 4. API

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| POST | `/api/sessions` | 세션 생성 → 무작위 토큰 |
| GET | `/api/tracks/search?q=` | 곡 검색 (DB → MusicBrainz) |
| POST | `/api/sessions/{token}/seeds` | 고른 곡 3~5개 저장 |
| POST | `/api/sessions/{token}/upload-url` | S3 서명 URL 발급 (JSON만, 크기 상한) |
| GET | `/api/sessions/{token}` | 상태와 단계별 건수 (화면이 몇 초마다 조회) |
| GET | `/api/sessions/{token}/stats` | 기본 통계 |
| DELETE | `/api/sessions/{token}` | 즉시 삭제 (DB + S3) |

### 4-1. API 상세 (2026-10-25 승인)

**공통**: JSON, 오류는 `{"code": "...", "message": "..."}`. 토큰은 32바이트 무작위(base64url 43자), DB에는 SHA-256 해시만. 만료(30일)는 404와 같게 처리. 접근 로그에서 토큰을 가린다.

**세션 상태**: SEEDS `CREATED → DONE` / TAKEOUT `CREATED → UPLOADING → PROCESSING → DONE | FAILED`

| API | 요청 | 응답 | 조건·오류 |
|---|---|---|---|
| `POST /api/sessions` | `{"entry": "TAKEOUT"\|"SEEDS"}` | 201 `{token, entry, status, resultUrl: "/r/{token}", expiresAt}` | |
| `GET /api/tracks/search?q=&limit=10` | | 200 `{items: [{title, artist, mbid?, listeners?}], source: "lastfm"}` | q 2~100자. **Last.fm 검색 + 서버 재정렬**(4-2장). 3초 초과·차단·키 없음 시 503 `SEARCH_UNAVAILABLE`. DB 먼저 검색은 L2 |
| `POST /api/sessions/{token}/seeds` | `{tracks: [{mbid?, title, artist}]}` 3~5개 | 200 `{status: "DONE", count}` | SEEDS·CREATED만. **mbid는 선택**(있으면 UUID 형식). 같은 곡(제목·가수가 같음) 중복 불가. 제목·가수는 재검증 안 함(자기 세션에만 영향) |
| `POST /api/sessions/{token}/upload-url` | `{totalCount, musicCount, unclassifiedCount, byteSize}` | 200 `{uploadId, url, method: "PUT", headers, expiresAt}` | TAKEOUT·CREATED만 → UPLOADING. **20MB 초과 413 `TOO_LARGE`**. 서명 10분, 크기를 서명에 포함. 키는 `uploads/{uploadId}.json` |
| `GET /api/sessions/{token}` | | 200 `{entry, status, counts: {total, music, unclassified, saved}, period, seeds, error, createdAt, expiresAt}` | 화면이 **2초마다** 조회 |
| `GET /api/sessions/{token}/stats` | | 200 `{period, totals, topTitles(20), topChannels(20), byHour, byWeekday, byMonth, bySource, coverage}` | DONE이 아니면 409 `NOT_READY`, SEEDS면 409 `INVALID_STATE`. 시간대는 한국 시간, 채널의 ` - Topic`은 떼고 합침 |
| `DELETE /api/sessions/{token}` | | 204 | S3 먼저 삭제 → DB 삭제(연쇄). S3 실패 시 502 `STORAGE_ERROR`, DB 유지 |

**브라우저가 올리는 파일** (원본이 아니라 필터를 거친 것):
`{"schemaVersion": 1, "items": [{"videoId", "title"(시청 문구를 뗀 제목), "channel", "watchedAt", "source": "MUSIC_APP"|"YOUTUBE"}]}`

**워커(parse)**: `s3:TestEvent` 무시 → upload가 이미 PROCESSED면 건너뜀 → 세션 PROCESSING → 검증·묶음 저장 → 저장 건수·기간 기록 → DONE. 실패 시 FAILED + 오류 메시지, 3번 실패한 메시지는 실패 큐로.

**워커 구현에서 정한 것 (2026-10-25)**
- **영구 오류와 일시 오류를 나눈다.** 파일 형식 오류(JSON 아님, schemaVersion 다름, 유효 항목 0개)는 재시도해도 같으므로 바로 FAILED로 끝내고 메시지를 지운다. S3·DB 연결 오류는 예외를 던져 큐가 다시 시도하게 하고, 3번 실패하면 실패 큐로 간다.
- **저장은 한 트랜잭션.** 업로드 PENDING → PROCESSED 잡기, 청취 기록 묶음 저장, 세션 DONE을 한 번에 한다. 중간에 죽으면 아무것도 남지 않아 재시도해도 중복이 없고, 동시에 두 워커가 같은 파일을 잡아도 하나만 저장한다.
- 잘못된 항목(빈 제목, 시각·출처 형식 오류, 영상 ID 형식 오류)은 건너뛰고 건수만 로그에 남긴다.
- S3 알림의 키는 URL 인코딩되어 오므로 풀어서 쓴다. `uploads/` 밖의 키와 업로드 기록이 없는 키(세션 삭제 등)는 건너뛴다.
- **남은 일 (L2)**: 실패 큐로 간 메시지의 세션은 PROCESSING에 머문다. 실패 큐를 보고 세션을 FAILED로 바꾸는 처리와 알림을 L2에서 붙인다.
- 측정 (로컬, 음악 25,362건·3.9MB): 워커 처리 2.7초, 업로드부터 DONE까지 4.5초, 통계 응답 0.81초. 통합 테스트(컨테이너)에서는 25,409건 1.6초.

**오류 코드**: 400 `VALIDATION` / 404 `SESSION_NOT_FOUND` / 409 `INVALID_STATE`, `NOT_READY` / 413 `TOO_LARGE` / 502 `STORAGE_ERROR` / 503 `SEARCH_UNAVAILABLE`

### 4-2. 곡 검색 출처 결정 (2026-10-25)

**MusicBrainz는 즉시 검색에 맞지 않는다** (실측, 로컬 → musicbrainz.org)

| 검색 | 결과 | 응답 시간 |
|---|---|---|
| "태연 Rain" (단순 검색 모드) | 엉뚱한 곡 ("rain rain rain…") | 1.9초 |
| "다비치 거북이" | 시간 초과(2초) → 503 | 2초+ |
| 가수 검색 "다비치" / "태연" | 별칭으로 DAVICHI / TAEYEON 찾음 | 0.8초 / 5.9초 |
| 가수 ID + 곡명 "거북이" | 정확 | **12.4초** |

- 한국 가수는 영문 이름으로 저장되고 한글 이름은 별칭에만 있어, 곡 검색에서 한글 가수명이 걸리지 않는다. 가수 → 곡 두 단계로 찾으면 정확하지만 느리다.
- → **MusicBrainz는 L2의 백그라운드 곡 식별에 쓰고, A 입구 검색은 Last.fm으로 한다.**

**Last.fm 검색 정확도** (사이트 검색으로 측정, API 결과와 같다는 보장은 없음. 33개 표본, 원곡 기준 판정)

| 유형 | 개수 | 원곡 1위 | 원곡 3위 안 |
|---|---|---|---|
| 옛노래(90년대) | 4 | 4 | 4 |
| 인디·덜 알려진 곡 | 6 | 5 | 6 |
| OST | 2 | 2 | 2 |
| 영어 | 3 | 2 | 3 |
| 인기 K-pop | 4 | 1 | 3 |
| 일본어·로마자 | 4 | 1 | 4 |
| 한글 표기·소문자·모호한 제목 | 3 | 1 | 2 |
| 붙여쓰기·띄어쓰기·오타 | 4 | 0 | 0 |
| 부분·초성 | 3 | 1 | 1 |
| **합계** | 33 | **17 (52%)** | **25 (76%)** |

- 가수와 제목을 띄어 쓴 검색은 27개 중 25개에서 원곡이 3위 안. 응답 0.3~1.4초.
- 1위에 MV·댄스 연습·라이브·커버·가사 영상·업로더 이름이 자주 올라온다 (유튜브 영상 제목이 곡 이름으로 쌓인 데이터).
- 붙여쓰기·오타·글자 일부·초성은 0건. 단어 단위 검색만 된다.

**실제 Last.fm API로 다시 잰 결과** (2026-10-25, 같은 33개, track.search 30개 요청)

| | 원곡 1위 |
|---|---|
| API 결과 그대로 | 17 / 33 (52%) |
| **우리 다시 정렬 후** | **28 / 33 (85%)** |
| 후보 30개 안에 원곡이 있는 표본 | 28 / 33 → **있으면 모두 1위** |

- 사이트 검색(상위 3개만 봄)보다 후보가 많아 뉴진스·블랙핑크·볼빨간사춘기도 원곡을 찾았다. 남은 5개는 붙여쓰기 2·오타·부분("밤편")·초성으로 결과 0건 → L2 우리 DB 검색.
- 응답: Last.fm API 중앙값 303~342ms, 95% 789~896ms, 최대 1.3초. 우리 fetcher(다시 정렬 포함, 캐시 없는 첫 호출) 중앙값 270ms, 95% 715ms.
- 실제 API에서 발견해 고친 규칙: 제목·가수가 뒤바뀐 항목(`잔나비 / 주저하는 연인들을 위해`)이 가수 일치 가산점으로 1위에 오르던 문제 → 검색어가 가수 칸에만 맞고 제목에 하나도 안 맞으면 가산점을 줄임 (테스트 추가).

**ZARD 21곡 시험** (2026-10-25, 실제 API)

| 유형 | 개수 | 원곡 1위 |
|---|---|---|
| 일본어 원제목 (負けないで, 揺れる想い, 運命のルーレット廻して …) | 12 | 12 |
| 영어 제목 (Don't you see!, IN MY ARMS TONIGHT) | 2 | 2 |
| 제목만 (負けないで, 揺れる想い) | 2 | 2 |
| 로마자 (makenaide, yureru omoi) | 2 | 2 |
| 가수만 한글 ("자드 負けないで") | 1 | 1 |
| **제목을 한글로 ("마케나이데", "지지마")** | 2 | **0 (결과 0건)** |
| 합계 | 21 | **19 (90%)** |

- ZARD는 정렬 전에도 19개 모두 원곡 1위 (MV·직캠이 섞이지 않는 옛 일본 가수). 다시 정렬해도 순서를 지킨다 → 실제 API 상위 10개를 `lastfm-zard-samples.json`으로 테스트 자료화.
- 한글로 옮겨 쓴 일본 곡 제목(발음 "마케나이데", 뜻 "지지마")은 Last.fm이 못 찾는다. L1은 "일본 곡은 일본어 원제목이나 로마자로" 안내, L2는 사용자 유튜브 기록의 한글 병기 제목(`ZARD - 負けないで (지지마)` 등)을 곡 별칭으로 모아 우리 DB에서 찾는다.
- 응답 중앙값 287ms, 최대 1.5초.

**반영**
- L1: Last.fm에서 30개를 받아 **서버에서 다시 정렬**한 뒤 10개를 돌려준다 (규칙은 `backend/external-fetcher`의 `Reranker`, 33개 표본을 테스트 자료로 사용). 결과가 없으면 "가수와 곡 제목을 띄어 써 보세요" 안내.
- Last.fm 결과에는 MusicBrainz ID가 비어 있는 경우가 많다 → **고른 곡의 mbid는 선택 값**으로 바꾸고(V2 마이그레이션), 정확한 ID는 L2에서 MusicBrainz로 채운다.
- L2: 붙여쓰기·오타·부분·초성은 우리 DB의 유사도 검색(PostgreSQL pg_trgm, 초성 색인)이 맡는다.

## 5. 데이터 (L1에서 만드는 테이블)

| 테이블 | 내용 |
|---|---|
| `session` | 토큰, 입구(A/B), 상태, 단계별 건수, 만료 시각(30일) |
| `listen_event` | 영상 ID, 제목, 채널, 재생 시각, 출처(뮤직 앱/일반 앱), 만료 시각(7일). 곡 ID 칸은 비워 두고 L2에서 채운다 |
| `seed_track` | 고른 곡의 MusicBrainz ID, 제목, 아티스트 |

- DB 변경은 Flyway로 관리한다. pgvector 확장도 첫 마이그레이션에서 켜 둔다(실제로 쓰는 건 L3).
- 같은 업로드 메시지가 두 번 와도 중복 저장되지 않게 업로드 단위로 고유 제약을 건다.

## 6. 기본 통계 (곡 식별 전이라 "제목 + 채널" 단위)

- 기간, 총 재생 수
- 많이 들은 제목 20개, 많이 들은 채널(아티스트 추정) 20개
- 시간대별(새벽·출근·낮·저녁)·요일별 분포, 월별 추이 (한국 시간 기준)
- 유튜브 뮤직 앱과 일반 유튜브 앱 비율

## 7. 로컬 환경

| 용도 | 구성 |
|---|---|
| 평소 개발 (빠름) | docker compose로 PostgreSQL + pgvector와 LocalStack(S3·SQS) → 백엔드는 IDE에서 실행, 웹은 Vite 개발 서버 |
| L1 마무리 확인 | k3d에 `deploy/base` + `deploy/overlays/local`로 올려 같은 흐름을 한 번 확인 |

- LocalStack에서도 "S3 업로드 → SQS 메시지" 연결이 동작하므로 실제 AWS 없이 B 흐름 전체를 돌릴 수 있다.

## 8. 테스트

| 종류 | 대상 |
|---|---|
| 웹 단위 테스트 (Vitest) | 브라우저 필터 규칙 (뮤직 앱, Topic 채널, 삭제 영상, 시청이 아닌 활동, 한국어·영어 시청 문구, 검색 기록 파일 거절) |
| 백엔드 단위 테스트 (JUnit) | 업로드 JSON 검증, 통계 계산 |
| 통합 테스트 (Testcontainers) | PostgreSQL + LocalStack을 띄워 업로드 → 큐 → 저장 → 통계, 삭제 |
| 전체 흐름 (수동) | 가상 Takeout 5만 건으로 브라우저에서 처음부터 끝까지 |

## 9. 완료 기준

1. 가상 Takeout 5만 건으로 B 흐름이 업로드부터 통계 화면까지 동작한다.
2. A 흐름에서 검색해 3~5곡을 고르면 저장되고 결과 링크가 열린다.
3. 삭제 버튼을 누르면 DB와 S3에서 실제로 사라진다.
4. 통합 테스트가 통과한다.
5. k3d에 올려 같은 흐름을 1회 확인한다.
