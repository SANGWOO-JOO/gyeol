# L2 설계: 곡 식별 파이프라인 (2026-10-26 승인)

전체 설계(`docs/design-v3.md` 12장)의 L2 "식별 파이프라인(큐, 워커, 외부 호출기, 전역 캐시, LLM 묶음 호출)"에 L1에서 미룬 일을 합친다.

## 1. 목표

"제목 + 채널" 단위 통계를 **곡·가수 단위**로 바꾼다. 결과 화면은 "밤편지 · 아이유" + 원곡 음반 표지로 보이고, L3 추천이 쓸 곡 ID(MusicBrainz)가 생긴다.

## 2. 처리량 문제와 방침

| 항목 | 값 |
|---|---|
| 실제 규모 한 사람의 음악 기록 | 25,409건, 고유 곡 4,628개 (`docs/l1-design.md`) |
| MusicBrainz 제한 | 초당 1회 |
| 곡 하나 식별 (4-3 측정) | 3~10초, 호출 2~15번 |
| 전부 식별하면 | 4~13시간 (추정) |

가상 파일(실제 통계에 맞춘 9.6만 건)로 계산한 **상위 N곡이 덮는 재생 비율**:

| N | 100 | 200 | 300 | 500 | 1000 |
|---|---|---|---|---|---|
| 재생 비율 | 57.8% | 65.7% | **70.3%** | 76.3% | 84.9% |

- 방침: **세션마다 재생 상위 N곡(기본 300)만 바로 식별**, 나머지는 하지 않거나 나중에. 실제 비율은 L2에서 측정해 조정한다(가상 데이터 기준 값이라 추정).
- 식별 결과는 **사용자끼리 공유하는 전역 캐시**(`title_alias`)에 둔다. 두 번째 사용자부터 같은 곡은 외부 호출 없이 찾는다.

## 3. 흐름

```
parse-worker (L1) ─ 저장 완료
   └▶ 고유 (제목, 채널) 집계 → 재생 순 상위 N개 → 캐시 적중은 바로 연결
        └▶ 나머지 SQS:identify (묶음)
                                ▼
identify-worker
 1. 캐시: title_alias(정규화한 제목+채널) 적중 → 끝
 2. 규칙: "가수 - Topic" 채널 → 가수 = 채널에서 " - Topic" 제거, 곡 = 제목
 3. LLM (Haiku 4.5, 묶음): 규칙이 안 통하는 것만 → {가수, 곡, 버전}  ← L2-3
 4. external-fetcher → MusicBrainz: 4-3 규칙 (가수 ID 확정 → 녹음 → 가장 이른 공식 음반)
 5. track·artist 저장, title_alias 기록(못 찾음도 기록), listen_event.track_id 연결
   └▶ 표지는 낮은 우선순위로 따로 (L2-2). 화면은 글자 타일로 먼저 표시
```

- 결과 화면은 L1 통계를 먼저 보여 주고, 식별이 진행되는 대로 곡 단위로 바뀐다("곡 확인 중 120/300").
- L1 음악 기록은 전부 Topic 채널 또는 뮤직 앱이라 대부분 2번 규칙으로 풀린다. LLM은 주로 일반 유튜브 영상(`[MV] 아이유(IU) _ 밤편지`)에 필요하다.

## 4. 데이터 (계속 보관하는 전역 데이터)

| 테이블 | 내용 |
|---|---|
| `artist` | MBID, 이름, 별칭(한·영·일) |
| `track` | 녹음 MBID, 곡명, 가수, 원곡 음반(MBID·이름·발매일·종류), 표지 주소 |
| `title_alias` | 정규화 키 → track 또는 "못 찾음", 방법(규칙/LLM/수동) |

`title_alias`에는 음악 제목과 채널 이름만 들어가고 사용자와 연결되지 않는다.

## 5. 작업 묶음과 순서

| 순서 | 묶음 | 내용 | 외부 의존 | 비용 |
|---|---|---|---|---|
| 1 | **L2-1 식별 파이프라인** | identify 큐·워커, 규칙 + MusicBrainz 식별, 전역 캐시, 상위 N곡, 진행 표시, 실패 큐 → FAILED | MusicBrainz | 0 |
| 2 | **L2-2 곡 단위 결과 화면** | 곡·가수 순위, 원곡 음반 표지(4-3), 고른 곡(A 입구)도 식별 | Cover Art Archive | 0 |
| 3 | **L2-4 우리 DB 곡 검색** | pg_trgm·초성·한글 별칭으로 식별된 곡 검색, Last.fm보다 먼저 | 없음 | 0 |
| 4 | **L2-3 LLM 제목 정리 + 일반 영상 음악 판정** | Haiku 묶음 호출(tool use 스키마 + 자체 검증, 가짜 응답 모드), YouTube Data API로 미분류 영상 판정 | Bedrock, YouTube API 키 | 사용자 한 명당 약 $0.5~1 (추정) |

**L2-3 개인정보**: 일반 영상 제목은 서버로 보내지 않는다는 원칙을 지키려고 두 단계로 한다. ① 브라우저는 영상 ID만 보냄 → ② 서버가 YouTube API로 음악 여부만 알려 줌 → ③ 브라우저가 음악으로 판정된 항목만 제목을 보냄.

**L2-3 전 사용자 준비**: Bedrock 모델 사용 확인, YouTube Data API 키 발급.

## 6. 측정할 숫자

- 식별 정확도: 정답 세트(`tools/cover-art/samples.json` 확장)로 단계별 정답률
- 전역 캐시 적중률, 두 번째 사용자의 처리 시간
- 상위 N곡이 덮는 재생 비율(실제 파일), 첫 곡 단위 화면까지 걸리는 시간
- LLM 토큰과 비용 (사용자 한 명당)
- MusicBrainz 초당 1회 제한이 병목이 되는 모습 (EKS 회차 ③ "외부 한도 병목" 실험과 연결)

## 7. L2-1 구현 결과 (2026-10-26)

**구성**: V4 마이그레이션(`artist`·`track`·`title_alias`·`identify_target`), fetcher `POST /internal/musicbrainz/identify`, worker `IdentifyPlanner`(parse 직후 상위 N곡 → 캐시 적중 처리 → identify 큐) · `IdentifyListener`(묶음 10곡, 동시 2) · `DeadLetterListener`(parse·identify 실패 큐 → FAILED), 세션 응답 `identify` 진행률, 결과 화면 진행 막대. worker 역할은 `WORKER_ROLE=parse,identify`.

**식별 정확도** (`tools/identify-eval/eval.mjs`, 실제 MusicBrainz, 가수는 한글 이름으로만)

| 단계 | 확실한 29곡 중 원곡 음반 일치 |
|---|---|
| 측정 도구 규칙을 그대로 옮김 | 26 |
| + 리믹스·라이브 녹음을 뒤로 (녹음 제목 괄호·설명 확인) | 27 |
| + 언어판 설명("Korean version")은 원곡으로, 같은 날이면 앨범 → EP → 싱글 | **28** (측정 도구와 같음) |

- 남은 1곡은 난춘(MusicBrainz 연결 누락, 4-3과 같음). 37곡 모두 찾음, 곡당 평균 5.0초·호출 2.1번.
- 찾은 함정: Coldplay "Yellow"는 "Yellow (The Alpha remix)" 녹음이 괄호 앞 제목으로 통과해 리믹스 음반이 골라졌다. 응답 순서가 매번 달라 결과도 흔들렸다(처음엔 *Mince Spies*).

**k3d 측정** (실제 MusicBrainz, fetcher 1개)

| 항목 | 값 |
|---|---|
| 실제 곡 37개(재생 814건) 첫 세션: 업로드 → 37곡 식별 | 약 110초, 37곡 모두 찾음, 청취 기록 814건 모두 곡에 연결 |
| 같은 파일 두 번째 세션 (전역 캐시) | **0.4초**, 외부 호출 0번 |
| 실제 규모 가상 파일(음악 25,362건): 통계 표시까지 | 2.6초 |
| 같은 파일: 상위 300곡 확인 25% / 50% / 100% | 130초 / 261초 / **476초** (곡당 약 1.6초, 가상 곡이라 모두 "못 찾음") |

- 병목은 MusicBrainz 초당 1회 제한(fetcher 한 곳). worker를 늘려도 빨라지지 않는다 → EKS 회차 ③ "외부 한도 병목" 실험에서 그대로 보여 줄 수 있다.
- 테스트: fetcher 식별 단위 8, 규칙·키 단위 4, worker 식별 통합 3(계획·캐시·실패 큐), api 진행률.

## 8. L2-2 구현 결과 (2026-10-26)

**구성**: V5(`track.cover_checked_at`, `seed_track.track_id`), fetcher `POST /internal/coverart/front`(그 음반 → 같은 이름의 다른 판 → 없음), worker `CoverListener`(cover 큐, 곡마다 한 번, 없음은 30일 뒤 다시), 통계 `topSongs`·`topArtists`·`identified`, 고른 곡 식별(api가 커밋 뒤 identify 큐로), 결과 화면 표지·음반·연도·출처 표시. worker 역할 `parse,identify,cover`.

**표시 이름**: 사용자가 YouTube에서 본 이름 우선(가장 많이 나온 제목, Topic 채널의 가수 이름). MusicBrainz 공식 표기("IU", "밤편지 (Through the Night)")는 쓰지 않는다. 식별된 곡은 곡으로 합치고(같은 곡의 Topic·공식 채널 기록), 못 찾은 곡은 "제목 + 채널"로 순위에 섞는다.

**표지** (실제 곡 37개, 확인 방식별)

| 방식 | 찾음 | 곡당 평균 |
|---|---|---|
| Cover Art Archive 첫 응답(307)만 확인 | 36/37 → 이름 비교 수정 후 37/37 | 0.7초 |
| **이미지 주소까지 따라가 실제 이미지인지 확인** | **37/37** (6곡은 같은 이름의 다른 판) | 1.9초 |

- 바꾼 이유: 봄날(You Never Walk Alone)은 Cover Art Archive가 "있다"고 넘겨 준 이미지 주소가 500을 줬다. 화면은 글자 타일로 대체됐지만, 끝까지 확인하니 다른 판의 표지를 찾았다.
- 같은 이름 비교는 문장부호를 무시한다("Every letter I sent you."). 다른 음반 표지로 대신하지 않는 규칙은 유지(단위 테스트).

**k3d 측정**

| 항목 | 값 |
|---|---|
| 실제 곡 37개 업로드(식별은 캐시) → 상위 20곡 표지 모두 표시 | 75.7초 (첫 응답만 볼 때 19.8초) |
| 새 곡 3개 고르기 → 식별 + 표지 | 14.3초 |

**운영 중 발견한 것**: MusicBrainz가 "바쁘다"(503)를 주면 fetcher가 세 번 다시 시도한 뒤 실패하고, 메시지는 표시 제한 시간(15분) 뒤에야 다시 처리됐다. 외부 503일 때는 메시지를 **30초 뒤** 다시 받도록 바꿨다(`gyeol.worker.busy-retry`). 15분은 실제로 오래 걸리는 정상 처리에만 쓴다.

## 9. L2-4 구현 결과 (2026-10-26)

**구성**: V6(`pg_trgm`, `track_search_term`(곡명·YouTube 제목·가수 이름·별칭·가수+곡 조합, 정규화와 초성), `track.plays_total`), V7(`fuzzystrmatch`), core `SearchText`·`TrackSearchRepository`(곡 저장·캐시 기록 때 색인, api 시작 때 빠진 곡 채움), api 검색 = 우리 DB 먼저 + Last.fm으로 채움, 검색 결과에 `trackId`·`coverUrl`, DB 곡을 고르면 식별 없이 바로 연결. 측정 도구 `tools/search-eval/eval.mjs`.

**점수와 순서**: 완전 일치 4 > 앞부분 3 > 부분 2 = 가수가 정확히 맞는 오타(편집 거리 2 이하) > 곡 제목 조각 유사도 1. 결과는 **DB 확실(2 이상) → Last.fm → DB 약함(1)**. 같은 곡은 DB 쪽만 남긴다. Last.fm 장애여도 DB 결과가 있으면 돌려준다.

**정확도** (L1 질의 표본 33개, 곡이 DB에 있는 상태, k3d)

| 단계 | 원곡 1위 | 비고 |
|---|---|---|
| Last.fm만 (L1) | 28/33 (85%) | 붙여쓰기·오타·부분·초성 실패 |
| + 우리 DB | 31/33 | 초성은 NFKC가 초성 글자 코드를 바꿔서, 오타는 짧은 단어라 조각 유사도로 못 잡음 |
| + 초성은 NFKC 없이, 가수가 맞을 때 제목 편집 거리 | **33/33 (100%)** | 응답 중앙값 약 280ms |

**가로채기 확인** (DB에 없는 곡 10개, 같은 가수의 다른 곡은 DB에 있음): 처음엔 **5/10이 DB의 다른 곡이 1위**("아이유 라일락" → 밤편지). 조각 유사도를 "가수+곡" 조합에도 썼기 때문. 곡 제목에만 쓰고 약한 결과를 Last.fm 뒤로 보내 **0/10**.

**한계**: 가수·곡을 한글로 옮겨 쓴 일본 곡("자드 지지마", "ZARD 마케나이데")은 DB에 그 표기가 없어 못 찾는다(ZARD 표본 한글 0/3, 일본어 원제목 6/6). 일반 유튜브 영상의 한글 병기 제목을 별칭으로 모으는 L2-3에서 다룬다. DB에는 누군가 식별한 곡만 있으므로 처음 보는 곡은 여전히 Last.fm에 기댄다.
